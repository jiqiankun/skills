# 交互式旅行攻略 HTML 生成器（无地图 · 移动优先）

把一次多日旅行的行程规划，渲染为**单个可直接双击打开、手机可顺畅浏览的 HTML 文件**：攻略内容为主体，**不内置任何地图模块**（无地图底图、无小地图、无坐标依赖）。默认进入「总览」，按需展开每日正文、景点攻略、备用方案。

## 何时使用

- 用户要「做一份 X 天 X 地旅游攻略 / 行程规划单 / 旅行计划 HTML」，并希望手机能直接看、能离线用。
- 用户强调：兼顾历史文化 / 美食 / 自然 / 夜生活；美食餐厅、交通方式+耗时、实用攻略；总览和准备清单；**移动端友好**。
- 用户明确**不要地图 / 去掉地图 / 移动端优先**时，本技能即标准形态（无地图、无需坐标）。

## 核心设计原则（务必遵守）

1. **单一文件、零外部依赖**：所有 CSS / JS / 数据**内联**，不引用任何 CDN `<script>`（无任何地图、无第三方库）。双击即开、离线可用。
2. **无地图模块**：页面**不渲染任何地图**（不放 `TMap`、不写地图 Key、不保留坐标连线），数据中**不含 `lat/lng` 坐标字段**。
3. **移动优先（Mobile-First）响应式**：CSS 以窄屏为默认，桌面用 `@media(min-width:...)` 增强。单栏布局；导航 Tab 横向滚动并吸顶；详情网格窄屏单列、≥560px 两列。
4. **高频直显，低频折叠**：Dashboard 高频信息直接显示；景点详细攻略 / 备用方案 / 附近推荐按需展开（`<details>` 或点击「展开攻略」）。
5. **配色稳定**：沿用 Stripe 风（浅色底 + 柔光渐变 banner），三类 POI 固定配色：景点=青绿、美食=珊瑚红、文化=紫罗兰、交通=中性灰。不要随意改主色。
6. **Travel-first（旅游优先，摄影从属）**：先生成并锁定完整旅游行程，再补充拍照信息。摄影/拍照/机位永远是行程确定后的**附属增强**：允许反向**微调**行程时间（仅 ≤30 分钟、且不动景点/顺序/餐住/交通衔接），**禁止过度调整**（详见「📷 拍照打卡信息」章节）。

## 工作流（逻辑顺序）

### Step 1 · 设计数据模型（无需坐标）—— 先只做旅游计划

按 `references/data-model.md` 的 schema 组织全部内容（总览 / 准备清单 / 每日 / POI / 美食 / 内部路线 / 附近推荐 / 备用方案）。**先想清楚数据再写 HTML**，字段缺失会导致渲染错位。

- POI **不含 `lat/lng` 坐标字段**（地图已移除、坐标无用途），不要为 POI 添加坐标。
- 交通方式（`move`）仍要写明「🚄 动车约2h」「🚕 打车约20min」等，这是攻略核心，与地图无关。
- **这一阶段不考虑摄影**：只依据到达/返程时间、交通、开放时间、游玩时长、轻松/紧凑节奏、用餐、休息、住宿、停车、门票、天气、体力来决定时间轴、景点顺序、用餐与住宿。

### Step 1.5 · 行程锁定后，补充拍照信息（附加增强）

完整行程确定后，遍历计划中的地点（景点、古镇村落、街区、山水观景台、景观餐厅/酒店、市集夜市），在**真正值得拍**的地点上挂可选 `photo_info`（1–2 个机位、一句手机拍法 + 可选的 ≤30 分钟微调建议）。详见「📷 拍照打卡信息」章节。停车场、交通中转、服务区、普通餐厅等不写。

### Step 2 · 生成单文件 HTML

- 结构、CSS 变量、组件规范见 `references/layout-spec.md`。
- 直接以 `assets/guide-template.html` 为骨架改写（已是无地图、移动优先的单文件骨架：banner + 吸顶横向滚动导航 + 总览/DAY/特产/准备清单四页切换 + 卡片展开逻辑）。
- 关键交互：顶部导航 **总览 / DAY1–DAYn / 特产 / 准备清单** 横向滚动并居中，切换时当前 Tab 自动滚入视野；点卡片「▾ 展开攻略」展开 POI 详情（停留/顺序/必看/📷拍照打卡/门票/预约/避坑/便民/内部路线/附近推荐）。不设任何日级独立摄影模块。
- 大型景区（九寨沟 / 黄龙 / 熊猫基地 / 冰雪大世界 / 亚布力）不要只当普通 POI：补 `internal` 内部游览路线（先去哪、如何乘车、哪段步行、优先级）。
- 不要引入 `map.qq.com` 的 `<script>`；不要写 `TMap`、`flyToPoi`、`drawDay`、`initMap` 等地图代码。

### Step 3 · 校验后交付

跑 Node 校验，全部通过再 `present_files`：

```bash
node -e 'const fs=require("fs");const h=fs.readFileSync("X.html","utf8");
const re=/gljs\?[^"\x27]*[?&]key=[A-Z0-9-]{20,}/;console.log("KEY_HIT(应为false):",re.test(h));
const m=[...h.matchAll(/<script>([\s\S]*?)<\/script>/g)];
require("fs").writeFileSync("c.js",m[m.length-1][1]);'
node --check c.js && echo SYNTAX_OK && rm c.js
```

校验项：`KEY_HIT` 必须为 `false`（无地图 Key）、内联 JS 语法、Dashboard/备用方案/内部路线/附近推荐/美食增强/📷拍照打卡/总览/准备清单 字段计数、无 `TMap`/`mapPanel`/`flyToPoi` 残留、photo_info 微调幅度抽查（不得出现 >30 分钟的时间改写）。中文匹配用 `Grep` 工具而非 node 内联（shell 编码会误判为 0）。

## 📷 拍照打卡信息（Photo Info · 轻量附属）

Photography is supplementary travel information.
**Travel experience always takes priority over photography.**
Photography recommendations should describe how to make the most of places **already included in the itinerary**, rather than deciding which places should be included.

### 两个模式

- **travel-first（默认）**：完整旅游规划 → 锁定行程 → 按地点补充拍照信息。普通「做攻略 / 行程规划」请求一律走这条路径。
- **photography-focused（仅当用户明确提出）**：用户明说「摄影旅行 / 旅拍 / 拍照为主 / 追日出 / 星空 / 专找机位 / 摄影路线」时，才允许摄影参与行程规划。默认不要进入该模式。

### 生成顺序（travel-first）

1. Complete the travel itinerary first.
2. Finalize attractions, timing, transportation, meals, accommodation, and pacing.
3. After the itinerary is finalized, inspect each planned place.
4. Add optional concise photo tips where the place has clear photography value.
5. Photography tips must not rebuild the itinerary（可以微调，不能过度）.

### 哪些地点值得挂 photo_info

**值得**：古村古镇、历史街区、古建筑、山川湖泊海滨、草原梯田花海红叶雪景、观景台、老街、夜景区域、城市地标、特色市集、有视觉特色的景观餐厅/民宿。
**不写**：普通停车场、高速服务区、交通换乘点、普通便利店、普通餐厅、无视觉特色的住宿。不要为了让页面「看起来完整」强行给所有地点加摄影内容。

### photo_info 结构（全部字段可选，挂在 POI 上，不建独立摄影对象）

```js
photo_info: {
  spots: [                                    // 1–2 个机位，不超过 2 个
    { location: "晒秋平台",                   // 景区内部具体位置，不是景区名
      subjects: ["古村","晒秋","人像"],        // 适合拍什么（轻量标签）
      tip: "手机 2x 拍屋顶层次，人站石板路一侧即可" }  // 一句普通游客可执行的拍法
  ],
  best_time: "日落前光线更柔和",               // 参考时间，仅供参考
  schedule_note: "对照当前行程的说明（见下）"
}
```

### 微调边界（核心规则：可以微调，不能过度）

摄影推荐**允许**反向微调行程时间，但一次微调必须**同时满足全部**条件：

- 时间偏移 **≤ 30 分钟**（如「到达从 16:30 微调到 17:00，赶日落前柔光」）；
- 不增删、不更换景点，不改变景点间顺序；
- 不影响交通衔接（不误车、不误末班索道/观光车）；
- 用餐与住宿安排不动（用餐最多顺延 15 分钟且必须写明影响）;
- 不要求提前起床追日出/晨雾、不深夜滞留（除非原计划本来就有）。

任何一条不满足 = **过度调整，禁止**；此时只能退回「顺手拍」写法：描述**当前时段**怎么把照片拍好，不改任何时间。

`schedule_note` 的两种标准写法：

- 无需调整：「当前安排 14:00–16:00 游览，下午侧光也适合正常拍摄，无需调整。」
- 可选微调：「想拍日落前柔光，可把到达从 16:30 微调至 17:00（约 +30 分钟，不影响 18:30 晚餐）；按原时间到也能拍。」

### 写作红线

- 每个地点 **1–2 个机位**；整个摄影模块篇幅不得超过该地点的景点介绍/推荐玩法。
- **手机优先**：只写 0.5x/1x/2x/3x、人像模式、夜景模式、网格线、低/高机位、对称、引导线、倒影等普通手机可完成的操作；不写光圈/快门/ISO/RAW/ND/CPL/焦段分析/后期调色（用户明确要专业摄影内容时除外）。
- 摄影信息只出现在**地点卡展开区**内（`.photo-info` 轻量小框）；不设「今日必拍 / 摄影时间轴 / 摄影路线 / 追光计划」等日级独立摄影模块。
- 餐厅、民宿等已有计划地点若本身有视觉特色，可加一句「📷 顺手拍」（如「二楼露台看古村屋顶，入住后顺手拍一张」），但不能因此换餐厅/换酒店/改入住时间。
- 旧 `photo` 一行摘要字段保留兼容；无 `photo_info` 的地点自动回退为该行。
- 标签（`subjects`）用小胶囊展示，移动端自动换行、不横向滚动，每地点不超过 4 个。

### 示例：婺源篁岭（travel-first，含合法微调）

行程先按交通与游玩确定：`14:30 篁岭（约 3h）→ 18:00 入住 → 19:00 晚餐`，随后再补：

```js
photo_info: {
  spots: [
    { location: "晒秋平台", subjects: ["晒秋","古村","人像"],
      tip: "手机 2x 拍屋顶层次，人站在石板路一侧即可" },
    { location: "天街高处", subjects: ["村落全景"],
      tip: "手机 1x 横拍，屋顶作前景、远山作背景" }
  ],
  best_time: "日落前 1 小时光线更柔和（仅供参考）",
  schedule_note: "想拍日落柔光，可把上山时间从 14:30 微调至 15:00（约 +30 分钟，仍赶得上 18:00 入住）；按原时间到下午侧光也能正常出片。"
}
```

禁止写成「建议 07:00 上山拍晨雾」（提前 7.5 小时 = 过度调整，且要求改变起床时间）。若用户明确说「我就是要拍晨雾」，才可按 photography-focused 重新规划该日。

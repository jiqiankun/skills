# 单文件旅行攻略

把合理、可执行的旅行计划交付为一个 HTML 文件。攻略内容优先；移动优先，兼顾桌面；采用浅色、柔和渐变的 Stripe 风格，以清晰层次、舒适阅读和目的地特色呈现完整攻略。页面不含地图模块，不需要经纬度；不要求离线使用。

## 入口与输入

- **规划并生成 HTML**：整理约束、核验信息、完成路线，再生成文件。
- **已有行程转 HTML**：保留用户的景点、顺序、已订交通和住宿；检查明显冲突，补充必要攻略。会改变硬约束的冲突先说明并询问，其他展示工作继续进行。
- “手机看的攻略”是使用意图信号，不单凭“不要地图”“移动优先”触发。用户只要聊天建议或纯文字时，不擅自扩大为文件制作。以多日旅行为主，也接受已有一日行程的渲染。

复用上下文，一次集中询问真正阻碍规划的信息；不要为了填满模板反复追问。

| 输入 | 缺失时的处理 |
|---|---|
| 目的地、可用天数 | 新规划必须明确；已有计划可从内容提取 |
| 出发地 | 安排往返交通时需要；只处理目的地内行程可省略 |
| 日期 | 精确票务、闭馆和季节安排依赖日期；未定日期可做通用方案，标明适用季节与待确认项 |
| 人数、成人儿童构成 | 用于预算、房间和点餐；未知时用人均／每间口径，不默认两人 |
| 往返交通、抵离时间和站点、已订住宿 | 已订内容属于硬约束；未订时给建议时间窗，不虚构班次 |
| 必去／可去／不去、饮食与住宿偏好、预算 | 已知则遵守；未知可用适中节奏、便利住宿区域和价格区间，并简述假设 |
| 老人儿童、体力、行李、无障碍、忌口等 | 集中确认是否存在影响路线的特殊约束；已知限制不得省略或擅自放宽 |
| 摄影 | 未提出需求时不启用专项增强；摄影为主须在规划开始时识别 |

## 规划规则

1. 按真实区域、入口出口和交通通达关系串成每日游览链；相邻不等于顺路。避免反复跨区；必要折返说明原因。无需坐标，也不把交通时间从页面中删掉。
2. 先排固定班次、预约和开放时段，再排景点、三餐、休息与住宿。逐段核对“前站结束 → 步行／换乘／车程 → 排队／入场 → 下一站开始”，门到门时间不能只写车内时间。
3. 首日计入出站或落地后的取行李、接驳和寄存／入住；末日从发车或起飞及检票／值机要求倒推，计入退房、取行李、安检和合理余量。区分到站时间与发车时间，晚到不排完整白天，早走不硬塞景点。
4. 明确每段的开始、结束或停留时长；跨午夜标明日期。早餐、午晚餐、等位与休息占用真实时间，小吃不自动替代正餐。车程和排队用合理区间，留出与旺季、交通方式匹配的缓冲。
5. 景点数服从时长和体力；大型景区可占完整一天。步行估算包括景区内部、台阶、坡度与连续站立，按同行人调整；提供可优先删减项，不安排所有“附近推荐”。
6. 两天一夜保护首尾交通、尽量不换住宿；三天两夜优先一个基地配一个完整核心日；更长行程按区域分段并穿插轻松时段。只有整体减少奔波才换酒店，不把这些策略当固定数量配额。
7. 住宿先选区域，再按需推荐具体酒店；联系前一天终点、次日第一站与返程节点。已订住宿作为路线约束；考虑早餐、夜宵、公共交通、停车和行李，不只写“市中心方便”。
8. 最终时间轴是总览和 Dashboard 的依据；景点数排除餐厅、车站、入住。总预算与分项、每日费用统一人数、币种、单程／往返及每间／每晚口径，说明未计费用，避免重复计费。

## 事实核验

生成阶段联网研究，页面可按内容需要使用在线图片与资料链接。优先官方运营方、景区、场馆、酒店及餐厅信息；复用已核验资料，只回查影响路线的新变化。正文中的动态事实仍须标注核验状态，不把联网能力等同于实时准确。

| 信息 | 要求 |
|---|---|
| 固定车次／航班、开放与闭馆、预约、最晚入场、末班接驳、施工或临时关闭 | 纳入主行程前优先核验；未来尚未公布时只能给时间窗和替代安排 |
| 门票、具体酒店与餐厅营业、入住条件 | 推荐具体对象时核验；价格注明查询日期、单位和条件，不把查询结果说成已预订 |
| 车程、排队、步行、餐饮花费 | 标为估算并说明影响因素；不编造精确等待时间 |
| 天气、季节性景观、日出日落 | 预报有效范围内标查询日期；远期用季节参考，不能编造逐日天气。光照与景观依日期和现场条件，不承诺“必有” |

- 对影响出行的结论保留来源名称、链接、核验日期和状态；关键限制就近直显，来源集中在总览。来源链接为结论提供依据，不能代替页面中的实际攻略。
- 区分“用户已确认”“已核验（日期）”“估算”“待确认”。无法核验时不编造地址、时间、价格或营业状态；说明影响及可执行替代，必要时只交付条件方案。
- 限制性事实未确认时，不用它支撑无余量的行程。不以“仅供参考”替代核验；携带／运输条件按物品和实际交通核验，不写“真空包装即可上机”等通用保证。

## 内容与摄影

组织攻略时读取 [内容与字段约定](references/data-model.md)：核心景点要讲清看点和玩法；美食嵌入餐次；住宿有地理理由；备用能够接回主线；特产写清购买地点与选择该渠道的理由。模块按适用性出现，不凑数量或空栏目。

内容深度优先于字段齐全：总览解释“为什么这样走”，每天有明确体验主题；核心景点用目的地特有的细节、可执行的游览建议和取舍支撑推荐。将“看点／玩法／交通衔接”写成连贯攻略，避免只写宣传形容词或景点名称。重要信息先给摘要，再在详情中展开；内容丰富不等于每个节点都写长文。

摄影规则只在此处维护：普通攻略可在合适地点附一句拍照提示，不默认生成摄影模块；用户明确需要时，在地点详情中加少量机位、时间／光线与拍法。手机优先，焦段、三脚架、器材等专业建议按需提供。日出日落、蓝调、建筑、夜景或人像只补与当前需求有关的内容。

普通旅行先完成路线，摄影只能利用余量；每次可选时间微调不超过30分钟，且不改景点顺序、不挤占用餐住宿或硬性交通。必须重新核算当天累计影响；不满足则保留原安排。摄影主导旅行从一开始将拍摄窗口作为约束，仍遵守开放、交通、休息和安全条件。摄影不另建独立页面，不重复输出“无需调整”等填充句。

## 生成与交付流程

1. **理解需求**：确定入口、硬约束、偏好与必要假设，补齐关键缺失项。
2. **核验并规划**：先查会改变路线的信息，完成可执行时间轴；再补景点、美食、住宿、备用、特产和按需摄影。
3. **组织页面并生成**：读取 [布局规范](references/layout-spec.md)，改写 [单文件模板](assets/guide-template.html)。直接将内容写入语义 HTML，不维护第二份运行时数据副本；模板占位符全部替换，移除无内容模块及对应导航。默认总览，可通过链接进入某日。
4. **集中验收**：检查下方完成标准；修正失败项后只重查相关部分。无需独立规划报告、JSON、中间确认或重复检索。
5. **输出一个 HTML 文件**：提供当前环境可访问的文件链接和简短打开说明，列出仍会影响出行的待确认项；使用在线图片等资源时注明需要联网。无需服务器、构建命令或配套代码文件。手机文件管理器是否允许交给浏览器打开，应按实际验证说明，不承诺所有内置预览器支持脚本。

## 完成标准

- 约束一致；日期、天数、人数和费用口径明确；首尾交通可衔接，活动与交通不重叠，路线基本顺路。
- 每个核心景点有实际玩法；住宿有地理理由；主要餐次与行程自然衔接；适用异常有替代动作，附近项明确为可选。
- Dashboard 的时间、景点数、步行、交通和预算与主行程一致；没有精确化的未知事实，关键结论有核验状态。
- 只交付一个 HTML，核心 CSS、JS 与正文内联，无地图与坐标依赖。可使用有来源的在线视觉资源和资料链接，不强制零网络依赖；不为装饰增加运行框架、追踪器或不必要的实时接口。
- 本地 file:// 可打开；在线资源失败时不遮挡正文，图片有替代文字。JS 禁用或启动失败时仍有完整正文、锚点导航和原生折叠；无空栏、占位符或重复 ID，导航目标存在。
- 在360、390、430px及桌面宽度检查长标题、全部展开、文字放大和横向溢出；点击区域、键盘焦点、切页及返回正常，吸顶导航不遮挡内容。
- 浏览器有条件时实际检查 Chromium 和 Safari／WebKit；未测试的平台如实说明，不把语法检查或响应式模拟当成实机通过。

维护模板交互时可运行 [模板回归检查](scripts/check-template.cjs)（Node 与可用的 Playwright 浏览器环境）；它不验证旅游事实，也不替代最终攻略的内容与实机检查。无需为生成单份攻略安装测试框架。
